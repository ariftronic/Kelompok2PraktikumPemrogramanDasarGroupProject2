2. DESKRIPSI SISTEM
---------------------------------------------------------------------
Laboratorium menyediakan peralatan yang dapat dipinjam mahasiswa.
Aplikasi berbasis Python (OOP) ini mencatat mahasiswa, peralatan,
transaksi peminjaman (satu transaksi boleh berisi beberapa alat), dan
pengembalian alat (boleh sebagian) beserta kondisinya. Seluruh data
disimpan permanen di text file (.txt).

Aturan bisnis:
1. Alat yang tidak tersedia tidak dapat dipinjam.
2. Maksimal dua transaksi aktif per mahasiswa.
3. Satu transaksi dapat memuat beberapa alat.
4. Pengembalian boleh sebagian; status transaksi menjadi
   "sebagian dikembalikan" sampai semua alat kembali.
5. Alat yang dikembalikan rusak ringan atau rusak berat tidak kembali
   menjadi tersedia.
6. Mahasiswa atau alat yang masih ada di transaksi aktif tidak dapat
   dihapus. Yang tercatat di riwayat transaksi juga tidak dapat
   dihapus (lebih ketat dari teks aturan, demi konsistensi data).
7. Data di memori dan di file harus selalu sama.
8. Transaksi harus merujuk NIM dan kode alat yang ada.
Tambahan: batas pengembalian maksimal 7 hari; status aktif mahasiswa
diatur otomatis ("aktif" selama punya transaksi aktif); keterlambatan
dihitung dan dicatat di log.

Alur data:
- Saat program mulai, semua file dibaca dan dimuat ke list/dict
  (urutan: alat, mahasiswa, transaksi).
- Setiap tambah, edit, hapus, transaksi, dan pengembalian langsung
  ditulis kembali ke file.
- Operasi yang ditolak aturan bisnis tidak mengubah isi file.

Tantangan yang dipilih:
- Tantangan A: Pencarian fleksibel (alat berdasarkan kode, sebagian
  nama, atau kategori).
- Tantangan D: Log activities (log.txt, mode append).

3. STRUKTUR PROGRAM
---------------------------------------------------------------------
main.py                    titik masuk, memanggil menu utama
app/
  konstanta.py             pemisah, path, nama kolom, string status dan
                           kondisi, aturan bisnis
  file_manager.py          satu-satunya tempat open()/with/try-except
  logger.py                log aktivitas ke log.txt (append)
  validasi.py              helper validasi input
  menu.py                  tampilan menu dan alur interaksi
                           (tanpa logika bisnis)
  models/                  Mahasiswa, Alat, Transaksi, DetailTransaksi
  manager/                 manager_mahasiswa, manager_alat,
                           manager_transaksi, manager_pengembalian
data/                      file penyimpanan (.txt)
data_sampel/               contoh data (5 mahasiswa, 10 alat, 3 transaksi)
docs/                      UML final dan individu, kontrak antarmodul,
                           keputusan desain, pengujian, bukti eksekusi,
                           code review, refleksi
tests/                     pengujian otomatis (unittest) dan skrip
                           skenario wajib

Rancangan class:
- Model (Mahasiswa, Alat, Transaksi, DetailTransaksi): menyimpan data,
  memvalidasi baris file (dari_baris) dan membuat baris file (ke_baris).
- Manager (Mahasiswa, Alat, Transaksi, Pengembalian): menyimpan data di
  dictionary (kunci NIM, kode alat, ID transaksi) sehingga pencarian
  O(1) dan duplikat langsung terdeteksi; menerapkan aturan bisnis;
  memicu penyimpanan.
- Transaksi berisi list DetailTransaksi karena jumlah alat per
  transaksi dinamis dan urutannya dipertahankan.
- FileManager: pusat seluruh baca/tulis file, sehingga kode tidak
  berulang dan penggantian penyimpanan hanya menyentuh satu tempat.
- Logger: dipisah agar kegagalan log tidak menggagalkan operasi.
- Pelanggaran aturan dilempar sebagai ValueError dan ditampilkan menu
  sebagai [DITOLAK].

4. FORMAT TEXT FILE
---------------------------------------------------------------------
Aturan umum: satu baris mewakili satu data, kolom dipisahkan tanda
"|", tanpa baris judul. Kolom tanpa nilai ditulis "-". Tanggal
berformat YYYY-MM-DD. Karakter "|" dan baris baru tidak boleh ada di
dalam nilai data.

File                   | Kolom
mahasiswa.txt          | NIM|nama|no_hp|status_aktif
alat.txt               | kode|nama|kategori|kondisi|status
transaksi.txt          | id|nim|tgl_pinjam|batas_kembali|status
detail_transaksi.txt   | id|kode|status|kondisi|tgl_kembali
log.txt                | [YYYY-MM-DD HH:MM] teks bebas

Nilai yang diizinkan:
- batas_kembali      : 0 sampai 7 hari setelah tgl_pinjam
- status_aktif       : aktif | tidak aktif
- kondisi alat       : baik | rusak ringan | rusak berat
- status alat        : tersedia | dipinjam | tidak tersedia
- status transaksi   : dipinjam | sebagian dikembalikan | selesai
- status detail      : dipinjam | dikembalikan

Contoh isi (dari data_sampel/):
  # mahasiswa.txt
  M001|Andi Pratama|081234567890|aktif
  M002|Budi Santoso|081298765432|tidak aktif
  # alat.txt
  A001|Multimeter Digital|pengukuran|baik|dipinjam
  A004|Breadboard|prototyping|rusak ringan|tidak tersedia
  # transaksi.txt
  T001|M001|2026-11-02|2026-11-09|dipinjam
  T003|M003|2026-11-03|2026-11-10|sebagian dikembalikan
  # detail_transaksi.txt
  T003|A004|dikembalikan|rusak ringan|2026-11-05
  T003|A005|dipinjam|-|-
  # log.txt
  [2026-11-10 10:15] Mahasiswa M001 ditambahkan

Perilaku pembacaan dan penulisan:
- File yang belum ada dibuat otomatis tanpa error.
- File kosong dianggap tanpa data.
- Baris yang kolomnya tidak sesuai, data ganda, atau rujukan yang tidak
  ada dilewati dengan peringatan [PERINGATAN]; program tetap berjalan.
  Baris yang dilewati tidak ikut tersimpan saat file ditulis ulang.
- Dibaca sekali saat program mulai; ditulis ulang utuh pada setiap
  perubahan dan sekali lagi saat keluar (menu 0).
- Hanya log.txt yang memakai mode append.
- Penulisan ulang memakai file .tmp lalu os.replace, sehingga
  kegagalan di tengah penulisan tidak merusak file lama.

Alasan memilih format:
- Pemisah "|" mudah diurai dengan split()/join() (json, csv, dan
  pickle tidak dipakai) dan jarang muncul di nama atau kategori.
- "-" untuk nilai kosong menjaga jumlah kolom tetap sehingga baris
  rusak mudah dikenali.
- detail_transaksi.txt dipisah dari transaksi.txt agar jumlah alat
  dinamis dan pengembalian sebagian tercatat per alat.

7. KENDALA DAN SOLUSI
---------------------------------------------------------------------
1. Status turunan (status alat, status transaksi, status aktif
   mahasiswa) ikut tersimpan di file sehingga bisa tidak sinkron bila
   file diedit manual.
   Solusi: diperbaiki otomatis saat data dimuat, dengan peringatan.
2. Kegagalan menyimpan di antara dua penulisan file dapat membuat
   memori berbeda dari file.
   Solusi: simpan_semua() memuat ulang data dari file lalu melempar
   ulang error; kondisi alat dipulihkan bila penyimpanan pengembalian
   gagal.
3. Menghapus mahasiswa atau alat yang ada di riwayat transaksi
   membuat transaksi selesai terbuang saat data dimuat ulang.
   Solusi: alat dan mahasiswa yang tercatat di transaksi mana pun
   tidak dapat dihapus.
4. Status aktif mahasiswa bisa bertentangan dengan transaksi yang
   sebenarnya bila diedit manual.
   Solusi: diatur otomatis mengikuti transaksi aktif dan tidak dapat
   diedit.
5. Kode baca/tulis hampir sama pada ManagerMahasiswa dan ManagerAlat
   (muat, simpan, _simpan_atau_pulihkan).
   Status: dicatat sebagai bahan perbaikan (class dasar bersama).
6. Menu awalnya tidak tercakup tes.
   Solusi: ditambahkan tests/test_menu.py dengan input berskrip.

8. KETERBATASAN DAN PERBAIKAN YANG DISARANKAN
---------------------------------------------------------------------
- Setiap perubahan menulis ulang seluruh file (biaya linear terhadap
  jumlah data).
- Pemeriksaan riwayat memindai semua transaksi (O(n)).
- Tidak ada penguncian file untuk akses bersamaan.
- Baris yang dilewati saat muat hilang pada penyimpanan berikutnya.
- Denda keterlambatan belum ada; baru dicatat di log.
- Tidak ada transaksi atomik antarfile dan tidak ada versi format.
Prioritas perbaikan: (1) penyimpanan inkremental atau database,
(2) indeks di memori, (3) aturan denda keterlambatan.
